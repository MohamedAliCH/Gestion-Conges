Checklist validée

  • POST /api/documents/upload via MultipartFile
  • Validation type fichier PDF / DOCX (Tika)
  • Taille maximale 10 MB
  • Sauvegarde dans uploads/hr-documents/
  • Métadonnées en BDD (nom, chemin, type, date, uploadé par)
  • Pipeline RAG asynchrone (@Async)
  • Chunking + embeddings + pgvector
  • Accessible ROLE_ADMIN uniquement
  • Nom unique avec timestamp
  • Ancien document ré-uploadé : chunks nettoyés

RagPipelineServiceImpl.java

services/Impl/RagPipelineServiceImpl.java

Cœur du pipeline RAG : extrait le texte du document (Tika), le découpe en chunks, appelle l'API d'embeddings (Ollama), et stocke les vecteurs dans pgvector.

LigneCodeExplication

44@Value("${rag.embedding.model:nomic-embed-text}")Modèle d'embedding utilisé. nomic-embed-text produit des vecteurs de 768 dimensions — cohérent avec la colonne vector(768) en BDD.
47-50chunkSize = 500; chunkOverlap = 50;Taille d'un chunk en caractères (500) et chevauchement entre chunks (50). Le overlap évite de couper une phrase en plein milieu entre deux chunks.
55@Override
@Async("ragExecutor")

75documentChunkRepository.deleteByDocumentId(documentId);Nettoyage Supprime les anciens chunks si le document est ré-uploadé. Évite des doublons de vecteurs en base.

}		Pour chaque chunk : 1) persistance en BDD, 2) appel API embeddings, 3) stockage du vecteur. L'échec d'un embedding est non-bloquant (warn + continue).

doc.setErreur(null);		Pipeline terminé avec succès : statut PRET, erreur effacée. Le document est maintenant interrogeable via recherche sémantique.

BodyContentHandler handler = new BodyContentHandler(-1);
parser.parse(stream, handler, metadata, context);
}		Tika AutoDetectParser choisit automatiquement le bon parser (PDFParser ou OfficeParser) selon le fichier. handler(-1) = pas de limite de taille pour l'extraction.

start += chunkSize - chunkOverlap;
}		Sliding window chunking. Avance de (500 - 50) = 450 caractères à chaque itération, gardant 50 caractères de contexte commun entre chunks consécutifs.

AsyncConfig.java

config/AsyncConfig.java

Configuration du thread pool dédié au pipeline RAG. @Async sans configuration = thread pool partagé et non contrôlé — ici on isole le RAG dans son propre executor.

LigneCodeExplication
11@ConfigurationIndique à Spring que cette classe déclare des beans à enregistrer dans le contexte.
12@EnableAsyncCritique Active le support de @Async dans toute l'application. Sans cette annotation, @Async est silencieusement ignoré et le code s'exécute de façon synchrone.
14@Bean(name = "ragExecutor")Déclare un bean Executor nommé « ragExecutor ». C'est ce nom que @Async("ragExecutor") référence dans RagPipelineServiceImpl.
16executor.setCorePoolSize(2);2 threads toujours actifs. Permet de traiter 2 documents en parallèle sans délai.
17executor.setMaxPoolSize(4);En cas de pic, jusqu'à 4 threads peuvent être créés.
18executor.setQueueCapacity(50);File d'attente de 50 tâches si les 4 threads sont occupés. Au-delà, une exception RejectedExecutionException est levée.
19executor.setThreadNamePrefix("rag-pipeline-");Préfixe des noms de threads (rag-pipeline-1, rag-pipeline-2…). Facilite le debugging dans les logs.
